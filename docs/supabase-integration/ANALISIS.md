## Modelo de negocio y correspondencia PostgreSQL

La tabla reúne atributos del esquema SQLite comprobado y el DDL propuesto en `supabase/migrations/`. Los tipos de la migración convierten IDs a `bigint generated by default as identity`, fechas a `timestamptz` y estados booleanos a `boolean`. Los importes se conservan como centavos enteros `bigint` para evitar redondeos y cambios del contrato API. La migración separa `order_payments` de los importes para que la política de lectura no exponga el método de pago al cliente.

### Relaciones y reglas de borrado

- `roles 1:N users`; `roles N:M permissions` mediante `role_permissions`. El borrado está restringido por FK.
- `products 1:1 inventory`; `products 1:N order_items` y `products 1:N inventory_movements`.
- Un cliente (`users` con rol `customer`) tiene `1:N orders` mediante `cliente_id`; el creador operativo tiene `1:N` pedidos mediante `created_by`.
- Un repartidor (`users` con rol `delivery`) tiene `0:N orders`; cada pedido tiene cero o un repartidor en `repartidor_id`.
- `orders 1:N order_items`; cada línea puede tener `0:N personalizations`.
- `orders 1:0..1 delivery_info`, único por pedido; la API exige estos datos al crear un pedido de delivery.
- `orders 1:N order_status_history`; los registros enlazan a un actor `users`.
- `orders 1:1 order_financials` y `orders 1:1 order_payments`; se separan importes y método de pago por nivel de acceso.
- Los pedidos conservan el historial: no existe borrado físico en los flujos CRUD; cancelar es una transición controlada y devuelve stock de forma atómica.
- El producto se “elimina” mediante baja lógica (`active = false`). Los datos de entrega se separan por privacidad.
- Propuesta inicial para Supabase: no conceder borrado físico a los roles de aplicación; mantener histórico/auditoría, salvo las cascadas técnicas de personalizaciones cuando se borra una línea mediante un flujo expresamente autorizado.

### Cardinalidades del PDF

En las páginas 2–5, el PDF presenta Pedido como entidad central, titular cliente, asignación opcional de repartidor, líneas, personalizaciones y datos de delivery 1:1. Roles y permisos son admin, cajero, cocina, repartidor y cliente. La fuente describe la implementación SQLite existente y no propone entidades `clientes`/`repartidores` separadas.

## Estado actual, brechas y decisiones

1. **Proyecto remoto:** Supabase CLI `3.0.0` autenticada; proyecto BurgerFlow (`vwobduocgjcreulhebxb`, `sa-east-1`) activo y enlazado. El baseline actual confirma 11 productos/inventarios ficticios, cero cuentas/perfiles de prueba y cero pedidos.
2. **Auth:** se eligió Supabase Auth. `supabase config push --yes` aplicó únicamente `auth.enable_signup=false`, revisado con `supabase config diff`; se dejaron intactos los otros ajustes remotos de MFA, correo, pooler y Storage. El alta de usuarios de la aplicación usa el cliente Admin con una clave `sb_secret_` exclusivamente en el backend.
3. **Esquema/RLS aplicados:** `migration list --remote` confirma aplicadas `20261111000100`, `20261111000200` y `20261122000100`; las dos migraciones anteriores no se reaplicaron. `supabase/verify-schema.sql` confirma 14 tablas públicas con `rls=true`, 17 políticas y privilegios SELECT/INSERT/UPDATE/DELETE para `service_role` en las 14 tablas.
4. **Persistencia:** el modo existente `DATA_BACKEND=sqlite` sigue disponible y los datos locales no se modificaron ni copiaron. `DATA_BACKEND=supabase` utiliza Auth, perfiles/roles y operaciones remotas; SQLite conserva las sesiones del servidor. No hay migración automática de hashes bcrypt ni de datos de negocio.
5. **Transacciones e integridad:** RPC `create_order` calcula precios desde PostgreSQL y crea pedido, pagos, líneas, personalizaciones, movimientos, contacto e historial con descuento de stock en una transacción. `update_order_status` cambia estado y revierte inventario al cancelar en la misma operación. Reasignar el pedido hace que la política RLS deje de permitir acceso al repartidor anterior.
6. **Privacidad:** el contacto de entrega está en tabla RLS independiente; solo admin, cliente propietario y repartidor actualmente asignado lo leen. Cocina solo consulta pedidos activos y no recibe contacto, totales del pedido ni método de pago. Los precios de línea sí siguen presentes en el DTO de cocina, como en la API SQLite existente. El método de pago se separó de los importes; roles solo proceden de `public.users.role_id`, que el cliente no puede editar.
7. **Credenciales:** `SUPABASE_DB_PASSWORD` está presente en `.env` ignorado por Git y permitió las consultas CLI. Los indicadores confirman el formato de las claves API sin mostrar sus valores. La lectura pública con la clave publishable respondió HTTP 200. La clave secreta se usó solo en servidor para provisionar y limpiar cuentas/fixtures; no se reutilizó la clave legacy `service_role` mencionada en el historial.
8. **Verificación remota (2026-11-22):** `npx.cmd supabase projects list` confirmó BurgerFlow (`vwobduocgjcreulhebxb`, `sa-east-1`, `ACTIVE_HEALTHY`, enlazado). `migration list --remote` confirma las tres migraciones aplicadas. `verify-schema.sql` devuelve 14 tablas con RLS, 17 políticas y grants DML efectivos para `service_role` en todas las tablas. `test-baseline.sql` confirma actualmente 11 productos, 11 filas de inventario, cero Auth users/perfiles y cero pedidos.
9. **Pruebas:** `npm.cmd test` pasó 13/13 pruebas locales; las comprobaciones de sintaxis de `backend/app.js`, `backend/app.test.js`, `backend/server.js`, `backend/supabase-client.js`, `scripts/supabase-cli.js` y `scripts/supabase-remote-smoke.js` pasaron. El smoke remoto completo tuvo una ejecución `success=true` antes de cargar el catálogo y otra después; usó JWT normales de admin, cajero, cocina, dos repartidores y dos clientes. Verificó CRUD, entradas inválidas, permisos/denegaciones, reasignación A→B con 404 sin PII para A y dirección para B, cancelación/restauración de inventario y persistencia tras reiniciar. Dos intentos iniciales posteriores a la semilla tuvieron HTTP 500 intermitentes en solicitudes que esperaban 400/403; en uno falló la eliminación Auth automática y se limpió manualmente solo esa etiqueta. La ejecución completa final con semilla pasó las validaciones de estado esperadas y eliminó fixtures. El baseline final quedó con cero usuarios/perfiles/pedidos de prueba.
10. **Alcance conservado:** se aplicó con autorización `20261122000100_service_role_api_access.sql`, limitada a DML en las 14 tablas actuales y uso/lectura de secuencias; no se añadieron privilegios predeterminados para objetos futuros ni se modificaron políticas RLS. El catálogo ficticio se cargó después por instrucción del usuario y contiene 11 productos/inventarios; no hay usuarios ni pedidos de prueba. `DATA_BACKEND=sqlite` sigue siendo el valor habitual.

## Acceso CRUD propuesto e implementado en migraciones locales

- `anon`: solo `SELECT` de productos activos; altas públicas de Auth deshabilitadas.
- `authenticated`: perfiles propios; las operaciones restantes se limitan mediante RLS y funciones autorizadas.
- Admin: crear/leer/editar/desactivar productos; ajustar inventario; consultar operaciones y gestionar cuentas/activación; asignar repartidores. No existe borrado físico interactivo.
- Cajero: consultar catálogo, crear y consultar pedidos, cancelar según transición; no lee contacto/dirección.
- Cocina: consultar pedidos `pending/preparing/ready` y aplicar transiciones de cocina; no lee delivery, importes o método de pago.
- Repartidor: leer solo pedidos de delivery actualmente asignados y avanzar transiciones de entrega; la reasignación revoca acceso a quien deja de estar asignado.
- Cliente: catálogo, creación de pedido y lectura/edición de delivery solo en pedidos propios y pendientes.
- Auditoría: historial y movimientos se insertan dentro de las RPC; no se conceden operaciones directas de modificación o eliminación.

Las tablas, políticas y grants están aplicados en Cloud. El smoke test confirmó el comportamiento de autorización con sesiones JWT normales; el listado estático de políticas se complementa con respuestas reales de la API y el aislamiento de usuarios.
